## Confirmed architectural decisions

### Application style

- Модульный монолит.
- Backend и frontend находятся в одном репозитории.
- Используется единая PostgreSQL.
- Микросервисы и брокеры сообщений сейчас не требуются.

### Backend

- Python.
- FastAPI.
- SQLAlchemy 2.
- Alembic.
- Pydantic.
- PostgreSQL.

### Frontend

- Angular.
- Адаптивный веб-интерфейс.
- Отдельное мобильное приложение не входит в текущий scope.
- Offline-first режим не входит в текущий scope.

### Deployment

- Docker Compose.
- Application container и PostgreSQL.
- Единый HTTP entrypoint для production-подобного запуска.
- Приложение рассчитано прежде всего на доверенный контур.

### User model

- Один владелец приложения.
- Нет регистрации нескольких пользователей.
- Нет ролей.
- Нет permissions.
- Нет организаций и tenants.

### Financial data

- Для денег нельзя использовать `float`.
- Предполагаются `Decimal` в Python и `NUMERIC` в PostgreSQL.
- Баланс счёта должен вычисляться из журнала финансовых движений.
- Начальный остаток должен создаваться операцией корректировки.
- Все изменения одной операции должны быть транзакционными.

### Funds

- Фонд является виртуальным назначением реальных денег.
- Один фонд может находиться на нескольких физических счетах.
- Сумма процентов распределения активных фондов не должна превышать 100%.
- Перевод фонда между счетами не должен менять общую сумму фонда.

### Scheduled operations

- Ожидаемые операции не меняют фактический баланс.
- Фактическая операция появляется после подтверждения.
- Ожидаемый экземпляр можно подтвердить, перенести или отменить.

### Licensing

- AGPL-3.0-or-later.

## Known technical risks

### Financial invariants

Главный риск проекта — появление расхождения между:

- журналом операций;
- физическими остатками счетов;
- виртуальными остатками фондов;
- прогнозом;
- восстановленными из backup данными.

Финансовые инварианты должны проверяться на уровне application service и базы данных там, где это возможно.

### Editing operations

Свободное редактирование и удаление операций требует полного и атомарного пересоздания связанных движений.

Особенно внимательно необходимо обработать:

- переводы;
- операции с фондами;
- подтверждённые регулярные операции;
- платежи по долгам и кредитам.

### Rounding

Процентное распределение средств может создавать остаток из-за округления.

До реализации фондов должна быть принята единая политика:

- единица хранения;
- количество десятичных знаков;
- порядок распределения остатка округления.

### Scheduled materialization

Некорректная материализация может создавать дубли ожидаемых операций.

Необходимы:

- уникальный ключ;
- идемпотентный алгоритм;
- тесты повторного запуска.

### Backup compatibility

После появления публичных версий изменение структуры backup потребует версионирования и миграции импортируемых данных.
